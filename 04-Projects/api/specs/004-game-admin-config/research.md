## Decision 1: JWT `gameAdminRoles` — UUIDs vs Slugs

**Question**: `AccessTokenPayload.gameAdminRoles` currently stores game UUIDs from
`platform.games`. The `GameAdminCaroGuard` must check this array without a DB lookup
(Constitution Principle III). But UUIDs generated by `gen_random_uuid()` differ between
environments, making a hardcoded UUID in the guard fragile.

**Decision**: Change `GameAdminRoleTypeOrmRepository.findByAccountId()` to JOIN
`platform.games` and return game **slugs** instead of game IDs.

```
Before: gameAdminRoles = ['3f2a…uuid…']
After:  gameAdminRoles = ['caro']
```

**Rationale**:
- Slugs are human-readable and stable across environments (set explicitly in migrations).
- No config change needed — the guard simply checks `gameAdminRoles.includes('caro')`.
- Non-breaking: `gameAdminRoles` is not yet consumed by any guard in the codebase; this
  is the first game-specific role check being added.

**Alternatives considered**:
- Hardcode Caro game UUID in AppConfig: fragile (UUID changes if DB is reset).
- Store UUID in a constant file: same fragility problem.
- DB lookup in guard: violates Constitution Principle III.

**Impact**: Requires a one-line change to `GameAdminRoleTypeOrmRepository.findByAccountId()`:
join `platform.games` on `game_id = id` and return `slug` column.

## Decision 2: Duplicate Detection Strategy

**Question**: FR-009 requires rejecting creation (and reactivation — FR-011) of a
`(boardSize, moveTime)` pair that already exists as an **active** configuration.
Standard DB UNIQUE constraints would block deactivated+reactivated scenarios.

**Decision**: Use a **PostgreSQL partial unique index** on the `(board_size, move_time_seconds)`
pair filtered to `WHERE active = TRUE`.

```sql
CREATE UNIQUE INDEX uq_game_configs_active_combo
  ON caro_game.game_configs (board_size, move_time_seconds)
  WHERE active = TRUE;
```

**Rationale**:
- A partial index enforces uniqueness only among active rows; deactivated rows with the
  same combination co-exist without conflict.
- The DB handles the check atomically — eliminates race conditions from concurrent
  creates (CHK027 in api.md checklist) without application-level locking.
- Aligns with Constitution Principle IV: "atomic DB statement" for concurrent writes.
- Infrastructure adapter catches `QueryFailedError` with code `23505` (unique violation)
  and maps it to a domain `GameConfigDuplicateError`.

**Alternatives considered**:
- Application-level check (`SELECT … FOR UPDATE` before INSERT): adds round-trip and
  is a read-modify-write pattern — Constitution violation.
- Full unique index on `(board_size, move_time_seconds)`: blocks deactivated rows from
  sharing the same combination, preventing reactivation use cases.

## Decision 3: Caro Game Seed

**Question**: The Caro game does not yet exist in `platform.games` (current seeds:
League of Legends, Valorant, Teamfight Tactics). The Game Admin role assignment
(BRD-ACCOUNT-SOCIAL-001) and the guard both depend on the 'caro' slug existing.

**Decision**: The migration for this feature (`CreateCaroGameSchema`) seeds the Caro
game into `platform.games` with slug `'caro'` before creating the `caro_game` schema.

```sql
INSERT INTO platform.games (name, slug)
VALUES ('Caro', 'caro')
ON CONFLICT (slug) DO NOTHING;
```

**Rationale**:
- Single migration keeps the data dependency co-located with this feature's schema.
- `ON CONFLICT DO NOTHING` makes it idempotent (safe to run multiple times).

## Decision 4: Audit Fields (`createdBy`, `deactivatedBy`)

**Question**: FR-010 requires recording who created/deactivated each configuration.
The spec defines `createdBy` (identity) + `createdAt`, `updatedAt`, `deactivatedBy`
(identity) + `deactivatedAt`.

**Decision**: Store `created_by UUID` and `deactivated_by UUID` as plain columns
referencing the account ID from the JWT `sub` claim. No FK constraint to `account_social`
tables (cross-schema FK would violate modular isolation — Constitution Principle II).

**Rationale**:
- JWT `sub` is the account UUID; it is always present on authenticated requests.
- Cross-schema FK creates a deployment-order dependency and implicit coupling.
- Domain layer treats these as plain `string` (accountId) fields; the DB schema adds a
  comment for documentation only.

**Alternatives considered**:
- FK to `account_social.accounts`: violates module boundary (Constitution Principle II).
- Store email instead of ID: less stable, email can change.

## Decision 5: Reactivation Endpoint

**Question**: How to surface the reactivation operation (FR-011)? Options include
`PATCH /:id` with an `{ active: true }` body, or a dedicated sub-resource.

**Decision**: Dedicated endpoint `POST /admin/caro/game-configs/:id/reactivate`.

**Rationale**:
- Makes the intent explicit in the URL — no ambiguity about what `active: true` means.
- Separates the duplicate-check logic path from general update (FR-002 vs FR-011).
- Consistent with the "deactivate via DELETE" pattern — reactivation is the inverse.

## Decision 6: Module Schema & URL Pattern

**Schema name**: `caro_game` — consistent with `trust_report`, `account_social` naming.

**Admin URL prefix**: `/admin/caro/game-configs` — game-scoped admin namespace (allows
future `admin/lol/`, `admin/valorant/` analogues).

**Player URL**: `/game-configs` with query param `?game=caro` potential future extension,
but for now a dedicated endpoint: `GET /caro/game-configs` is cleaner. Since this is the
first game-specific endpoint, use `/caro/game-configs` to scope it to the Caro domain.

**Final URL decisions**:

| Endpoint | Method | Auth | Description |
|---|---|---|---|
| `/caro/game-configs` | GET | JwtAuthGuard | Player: list active configs |
| `/admin/caro/game-configs` | GET | JwtAuthGuard + GameAdminCaroGuard | Admin: list all (incl. inactive) |
| `/admin/caro/game-configs` | POST | JwtAuthGuard + GameAdminCaroGuard | Admin: create |
| `/admin/caro/game-configs/:id` | PATCH | JwtAuthGuard + GameAdminCaroGuard | Admin: update |
| `/admin/caro/game-configs/:id` | DELETE | JwtAuthGuard + GameAdminCaroGuard | Admin: deactivate |
| `/admin/caro/game-configs/:id/reactivate` | POST | JwtAuthGuard + GameAdminCaroGuard | Admin: reactivate |

## Decision 7: Cross-Cutting Change to account-social

**Summary**: `GameAdminRoleTypeOrmRepository.findByAccountId()` must be updated to return
game slugs. This is a one-line SQL change (add JOIN) in an existing infrastructure adapter
inside the `account-social` module.

**Scope**: Single method change. No new providers, no interface change, no module boundary
crossing. Can be done in the same PR as this feature or as a prerequisite task.
